# Research Report: r2py Ablation Protocol — Phase 2 (Submission-Script Remediation, Contamination-Vector Discovery, Isolation Redesign, and Production Submission)

**Repository**: `python-KernSmooth` (branch `main`)
**Session scope**: Line-by-line audit and repair of the three condition-specific SGE/Apptainer submission scripts (`submit_guides_replicates.sh`, `submit_no_guides_replicates.sh`, `submit_placebo_replicates.sh`); discovery and closure of two independent contamination vectors threatening the ablation's internal validity (reference-solution leakage via a pip-editable install, and Apptainer's default current-working-directory auto-bind exposing the entire repository including sibling replicates/conditions); redesign of the container invocation around explicit, narrow, same-path bind mounts; uninstallation of the `r2py_kernsmooth` package from the shared `r-to-python` conda environment; cleanup of a first, contaminated production run; explicit model-pinning (`--model claude-sonnet-5`) for experimental reproducibility; and two `qsub` submission events, the second of which is the corrected, currently-running production batch.

---

### 1. Abstract

This session began with a request to audit three newly drafted SGE submission scripts for Conditions G (guides), N (no-guides), and P (placebo) of the pre-registered ablation protocol, and ended with those scripts substantially redesigned, empirically validated, and submitted to the cluster as job-arrays **1222629** (guides), **1222630** (no_guides), and **1222631** (placebo), each `-t 1-10` (10 replicates), all currently in SGE `r` (running) state. In between, the session uncovered that the original container-invocation strategy (`apptainer exec --bind /groups`) silently exposed the entire repository — including the finished reference implementation `r2py_kernsmooth/` and every other replicate's/condition's output directory — to every headless conversion agent, via a mechanism (Apptainer's default auto-bind of the host's current working directory) distinct from the one originally suspected. A first production submission (jobs 1219841–1219843) was cancelled after this contamination was discovered from its logs and output. The fix — `--no-mount cwd` combined with an explicit, narrow, identical-source-and-destination `--bind` list per condition — was empirically validated via controlled dry-run tests before being wired into all three scripts, alongside a `pip uninstall` of the leaking package and explicit model-pinning. One unauthorized live (cost-incurring) smoke-test invocation was launched mid-session, immediately objected to by the user, and fully terminated and cleaned up before the final, corrected submission was made.

### 2. Methodology & Actions Taken

#### 2.1 Initial audit of the three submission scripts

- Reviewed `ablation/conversion_guides/submit_guides_replicates.sh` (pre-existing, tracked, 1,644 bytes, `755` permissions), `submit_no_guides_replicates.sh` (new, untracked, 1,742 bytes, `644` permissions), and `submit_placebo_replicates.sh` (new, untracked, 1,652 bytes, `644` permissions), all SGE array jobs (`-t 1-10`) invoking `apptainer exec --bind /groups "${IMAGE}" claude -p "/convert-r-file-to-python ..." --dangerously-skip-permissions`.
- Identified four concrete defects:
  1. **Job-name/log-path collision**: all three scripts used the identical SGE directives `-N ablation_guides` and `-o ablation/logs/guides_$TASK_ID.log`, inherited verbatim from the guides script via copy-paste — meaning concurrent or sequential runs of different conditions would overwrite or interleave each other's log files and be indistinguishable in `qstat`.
  2. **Stale header comments**: both new scripts retained the guides script's comment "Condition G (guides), primary tier, R=10 replicates" and its `qsub ablation/conversion_guides/submit_guides_replicates.sh` submit example, referring to the wrong script/condition.
  3. **Broken placebo guide path**: `submit_placebo_replicates.sh` passed the guide-directory argument as `/ablation/conversion_guides/placebo_conversion_guides/` — a leading-slash **absolute** path resolving from filesystem root, not from `REPO_ROOT`. Empirically confirmed `/ablation` does not exist at the filesystem root (`ls: cannot access '/ablation'`). The analogous guides-script argument, `language_dependency_analysis/conversion_guides/`, correctly has no leading slash.
  4. **Inconsistent permission bits**: the two new scripts were `644` (not executable) versus the guides script's `755`.
- Separately verified Claude account/authentication reachability inside the planned container: `/etc/apptainer/apptainer.conf` sets `mount home = yes` (confirmed via direct `grep`), so `$HOME` — including `~/.claude/.credentials.json` (504 bytes, refreshed 2026-07-23 10:56) and `~/.claude.json` (38,214 bytes) — is auto-bound into every container invocation with no extra flags required.
- Applied fixes: renamed job/log identifiers to `ablation_no_guides`/`no_guides_$TASK_ID.log` and `ablation_placebo`/`placebo_$TASK_ID.log`; rewrote the placebo guide-path argument to the relative `ablation/conversion_guides/placebo_conversion_guides/`; corrected both scripts' header comments and `qsub` examples; `chmod +x` on both new scripts. Re-verified via `bash -n` (all three passed) post-edit.

#### 2.3 Design discussion — closing the reference-leakage and cross-replicate "copycat" vectors

- Initial proposed remediation: exclude `r2py_kernsmooth/` from a scrubbed, non-git copy of the repository per task, combined with a private per-task fake `$HOME` to prevent Claude Code session-state races on the shared `~/.claude.json`.
- User clarified that concurrency/race conditions were **not** the actual concern; the real concern was that one replicate's already-generated output could be read and copied ("copycat") by another replicate's agent, since every task shared the identical `REPO_ROOT`, bound wholesale via `--bind /groups`, making every sibling replicate's and every other condition's `OUT_DIR` trivially visible via a relative `ls ../../guides/3`-style traversal.
- Refined proposed fix: replace the blanket `--bind /groups` with narrow, path-specific `--bind` flags (one per required input/output path), so that anything not explicitly listed — `r2py_kernsmooth/`, sibling replicates, other conditions — is simply absent from the container's mount namespace, not merely unvisited.
- User further suggested binding each required path to the **identical** absolute path inside the container (rather than remapping to a synthetic `/workspace` root), explicitly to minimize script changes: since the existing `claude -p` command lines already use paths relative to `REPO_ROOT`, keeping `--pwd "${REPO_ROOT}"` and binding paths 1:1 to themselves means no argument strings need to change.

#### 2.4 Empirical validation and discovery of the true isolation mechanism

- First empirical test of the narrow-bind approach — binding only `${REPO_ROOT}/KernSmooth` to itself, with no other flags — **failed to achieve isolation**: `ls` inside the container still showed `r2py_kernsmooth/`'s full contents, all ten sibling entries of `ablation/conversion_guides/guides/`, and the complete, unmodified listing of `REPO_ROOT` itself (`KernSmooth`, `LICENSE`, `README.md`, `ablation`, `conversion_results`, `docs`, `git_pull.sh`, `git_push.sh`, `install_environments.sh`, `language_dependency_analysis`, `r2py_kernsmooth`, `structural_analysis`) — none of which had been explicitly bound.
- Root-caused via two control tests: (a) with **zero** `--bind` flags and host cwd equal to `REPO_ROOT`, the entire repository was *still* fully visible inside the container; (b) with zero `--bind` flags and host cwd changed to `/tmp`, `REPO_ROOT` and `/groups` both correctly returned "No such file or directory." This isolated the actual mechanism: **Apptainer's default behavior of auto-binding the host's current working directory into the container** — not the `--bind /groups` flag used in every prior script version, and not any `apptainer.conf` bind-path entry (the earlier Phase 1 finding that "/groups is not auto-mounted" was correct only in isolation from this cwd-bind behavior; every script's own `cd "${REPO_ROOT}"` line, present since Phase 1, was what actually exposed the repository regardless of the explicit `--bind` flag's scope).
- Confirmed via `apptainer help exec` (version 1.5.0-1.el9, confirmed via `apptainer --version`) that `--no-mount cwd` disables this default, and that `--cwd`/`--pwd` (synonyms) set the container's initial working directory explicitly and independent of host cwd.
- Re-ran the narrow-bind test with `--no-mount cwd --pwd "${REPO_ROOT}"` added: `ls "${REPO_ROOT}"` inside the container now showed only `KernSmooth` (the one explicitly bound entry, with all other real directory entries absent); `ls "${REPO_ROOT}/KernSmooth"` succeeded with full real contents; `ls "${REPO_ROOT}/r2py_kernsmooth"` and `ls "${REPO_ROOT}/ablation/conversion_guides/guides"` (a sibling replicate parent) both correctly failed with "No such file or directory."
- Extended validation to the complete, realistic bind set needed for an actual conversion run — `${REPO_ROOT}/KernSmooth` (ro), `${REPO_ROOT}/structural_analysis` (ro), `${REPO_ROOT}/language_dependency_analysis` (ro), `${REPO_ROOT}/.claude` (ro — newly identified as a required bind, since the `/convert-r-file-to-python` slash command is defined in `.claude/commands/convert-r-file-to-python.md` and would otherwise be unresolvable inside the container), and one replicate's `${REPO_ROOT}/ablation/conversion_guides/guides/1` (read-write) — combined with `--no-mount cwd --pwd "${REPO_ROOT}"`. A pure `bash -c` dry-run (no `claude -p` invoked) confirmed: `pwd` correctly resolved to `REPO_ROOT`; all required relative-path reads succeeded (`KernSmooth/R/all.R`, `structural_analysis/R/all.json`, `structural_analysis/dependency_levels.csv`, `language_dependency_analysis/conversion_guides/` — listing all 46 real guide filenames — and `.claude/commands/convert-r-file-to-python.md`); a `touch`/`rm` round-trip inside `guides/1` confirmed write access; `ls ablation/conversion_guides/guides/2` (sibling) and `ls r2py_kernsmooth` both correctly failed.

#### 2.5 Uninstalling `r2py_kernsmooth` from the shared conda environment

- Per explicit user instruction ("for the `r2py_kernsmooth` package, you can simply uninstall it"), ran `"$HOME/.conda/envs/r-to-python/bin/pip" uninstall -y r2py_kernsmooth` — succeeded ("Successfully uninstalled r2py_kernsmooth-0.1.0"), executed as a background task due to slow filesystem I/O (task `b244fjhxp`).
- A follow-up host-side sanity check, `python -c "import r2py_kernsmooth"` (using that same conda env's interpreter), **still succeeded** despite the confirmed uninstall — `pip show`/`pip list` both confirmed no registered package remained. Root-caused to Python's `-c` flag implicitly adding the invocation's current working directory (`REPO_ROOT`, still containing the bare `r2py_kernsmooth/` source tree on disk) to `sys.path` — an import path entirely independent of pip's package registry.
- Re-ran the identical import test **inside the actual sandboxed container** (bind list explicitly excluding `r2py_kernsmooth/`, plus `--no-mount cwd --pwd "${REPO_ROOT}"`): both `import r2py_kernsmooth` and `import _KernSmooth` (the underlying compiled-extension module name) correctly raised import errors ("No module named 'r2py_kernsmooth'" / "No module named '_KernSmooth'"). This established that the bind-mount/cwd-auto-bind fix, not the `pip uninstall`, is the operative safeguard for actual job runs; the uninstall remains in place as defense-in-depth against any accidental interactive/host-side import.

#### 2.6 Rewriting all three submission scripts

- Replaced `apptainer exec --bind /groups "${IMAGE}"` in each of the three scripts with `apptainer exec --no-mount cwd --pwd "${REPO_ROOT}" "${BINDS[@]}" "${IMAGE}"`, where `BINDS` is a bash array constructed per script:
  - Common to all three: `--bind "${REPO_ROOT}/KernSmooth:${REPO_ROOT}/KernSmooth:ro"`, `--bind "${REPO_ROOT}/structural_analysis:${REPO_ROOT}/structural_analysis:ro"`, `--bind "${REPO_ROOT}/.claude:${REPO_ROOT}/.claude:ro"`, `--bind "${OUT_DIR}:${OUT_DIR}"` (read-write, this replicate's own output directory only).
  - `submit_guides_replicates.sh` additionally: `--bind "${REPO_ROOT}/language_dependency_analysis/conversion_guides:${REPO_ROOT}/language_dependency_analysis/conversion_guides:ro"`.
  - `submit_placebo_replicates.sh` additionally: `--bind "${REPO_ROOT}/ablation/conversion_guides/placebo_conversion_guides:${REPO_ROOT}/ablation/conversion_guides/placebo_conversion_guides:ro"`.
  - `submit_no_guides_replicates.sh` requires no additional guide-directory bind, since its "forbidden guides" instruction is inline prompt text with no associated filesystem path.
- Rewrote each script's explanatory header comment to describe the actual mechanism (`--no-mount cwd` disabling Apptainer's default cwd auto-bind; explicit same-path binds; nothing unlisted — `r2py_kernsmooth/`, sibling replicates, other conditions — existing inside the container namespace), replacing the now-inaccurate Phase-1-era comment claiming `/groups` needed manual binding due to `apptainer.conf`.
- Re-verified all three scripts via `bash -n` (passed) after every edit round in this section.

### 3. Key Findings & Results

- **Four concrete defects found and fixed** in the initial script drafts: job-name/log-path collisions across all three conditions; stale "Condition G" comments copy-pasted into the N/P scripts; a broken leading-slash absolute path for the placebo guide directory (`/ablation/...` instead of `ablation/...`, confirmed to resolve to a nonexistent filesystem-root path); and inconsistent executable permissions (`644` vs. `755`).
- **Two independent, previously-undetected contamination vectors** threatening the ablation's internal validity, both discovered from evidence in the first production run's logs/output rather than from static review alone:
  1. `r2py_kernsmooth` (the finished reference implementation) was pip-installed in **editable mode** in the exact conda environment (`r-to-python`) placed on `PATH` inside every job container, alongside the original R `KernSmooth` package with its compiled `.so` — making the reference solution directly importable/callable by any conversion sub-agent.
  2. **Apptainer's default auto-bind of the host's current working directory** — not the `--bind /groups` flag used throughout Phase 1 and the first Phase-2 submission — was the actual mechanism exposing the full repository (including `r2py_kernsmooth/` and every sibling replicate's/condition's output directory) inside every container, since every script's `cd "${REPO_ROOT}"` line triggered this default regardless of the explicit bind flag's scope. Root-caused via paired control tests (zero-bind-flags-from-`REPO_ROOT` vs. zero-bind-flags-from-`/tmp`).
- **Validated fix**: `--no-mount cwd` (disabling the auto-bind) plus `--pwd "${REPO_ROOT}"` (restoring correct relative-path resolution) plus an explicit, narrow, same-source-and-destination `--bind` list per condition (R source, dependency JSON/CSV, condition-specific guide directory, `.claude/` for slash-command resolution, and only the replicate's own output directory) — empirically confirmed, per-condition, to hide `r2py_kernsmooth/`, sibling replicates, and other conditions' output trees while preserving every existing relative-path argument unmodified.
- **`pip uninstall r2py_kernsmooth` alone is insufficient**: even after a confirmed-successful uninstall (`pip show`/`pip list` both empty), a bare host-side `python -c "import r2py_kernsmooth"` still succeeded, because Python implicitly adds the invocation's current working directory to `sys.path` and the source tree remained physically present on disk. The container-level bind-mount isolation (not the pip uninstall) is what actually blocks the import inside real jobs; the uninstall was retained as defense-in-depth.
- **Placebo guide corpus reconfirmed intact**: 46/46 filenames identical to the real guide corpus via `diff`, with no discrepancy (an earlier apparent 2-file count was a display artifact of a truncated listing, not a real defect).
- **SGE `long`-queue defaults carry an unmitigated cost-risk**: 720-hour (30-day) default runtime ceiling and no memory ceiling (`h_vmem`/`s_vmem` = `INFINITY`); flagged to the user but explicitly left unaddressed in this session per the user's direction to scope the final check to functional correctness rather than cost engineering.
- **`claude` CLI confirmed present and runnable (version `2.1.217`) inside the redesigned container for all three conditions**, verified via `command -v claude` and `claude --version` after an initial false-negative from a broken `which` binary in the minimal base image was root-caused and corrected for.
- **Process-discipline incident**: an unauthorized, real (cost-incurring) `claude -p` smoke-test invocation was launched in the background without prior explicit user authorization; the user objected immediately; the process (Apptainer parent PID 3860337, `claude` PID 3860362) was confirmed terminated via the `TaskStop` tool, and its partial output artifact (`_smoketest/`) was removed.
- **Model-pinning gap identified and closed**: no script or configuration file pinned an experimental model prior to this session; all three scripts now explicitly specify `--model claude-sonnet-5`, matching the interactive session's own model, per explicit user selection.
- **Two `qsub` submission events**: an initial submission (job-arrays 1219841/1219842/1219843) was cancelled via `qdel` after the contamination discovery in §2.2; a final submission (job-arrays **1222629**/**1222630**/**1222631**) followed all remediations above and is the currently-running production batch (30 tasks total, all in SGE `r` state as of session end).

### 4. Conclusion & Next Steps

The session's objective — auditing, repairing, and safely operationalizing the three condition-specific ablation submission scripts — is complete: job-arrays 1222629 (guides), 1222630 (no_guides), and 1222631 (placebo), 10 replicates each, are running under a redesigned container-isolation scheme that has been empirically validated (though not, per explicit user instruction, via a full authorized live end-to-end `claude -p` run — the only such run attempted was unauthorized, was terminated immediately upon objection, and its output was discarded) to prevent both reference-solution leakage and cross-replicate/cross-condition visibility, with the experimental model now explicitly pinned to `claude-sonnet-5` for reproducibility. Immediate next steps, several carried over unaddressed from this session: (1) monitor the 30 running tasks to completion via `qstat`/`ablation/logs/`; (2) upon completion, audit output completeness and correctness across all 30 `OUT_DIR`s before any downstream analysis, given that the *previous* run's superficially normal-looking output was exactly what had concealed the contamination bugs found in §2.2; (3) consider whether to retroactively add an explicit SGE `-l h_rt=` runtime ceiling and/or a `claude --max-budget-usd` cap to bound worst-case cost exposure, a gap identified but explicitly left unresolved in this session at the user's direction; (4) proceed to the protocol's subsequent stages once this primary-tier run is validated — the pre-registered pilot, the memorization probe, and the confirmatory-tier run on `rpart` — none of which were undertaken in this session.
