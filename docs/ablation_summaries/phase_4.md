# Research Report: r2py Ablation Protocol — Phase 4 (Pip Packaging-Metadata Remediation, Sequential Install/Test/Uninstall of 30 Ablation Replicates, and Variance-Aware Failure-Rate Aggregation)

**Repository**: `python-KernSmooth` (branch `main`)
**Session scope**: Diagnosis and repair of a repository-wide `pyproject.toml` packaging-metadata bug that blocked `pip install` for every package under `ablation/conversion_guides/` (and, it was discovered, for the reference `r2py_kernsmooth/` package itself); a sequential, 30-iteration install → `pytest` → uninstall cycle across all three ablation conditions (`guides`, `no_guides`, `placebo`) × 10 replicates each, executed as a backgrounded shell script against the `r-to-python` conda environment; parsing of the resulting 30 JUnit XML reports (including reconstruction of per-test results for one replicate that failed at test-collection time due to a broken import) into a per-test raw CSV and a three-tier, replicate-level mean/std summary CSV designed around the ablation protocol's actual experimental unit — the single replicate — rather than a pooled count across all tests; and relocation of all deliverables, per user correction, from `ablation/results/` to `ablation/conversion_guides/results/`.

---

### 1. Abstract

This session executed the build-and-test verification step explicitly flagged as unstarted at the end of Phase 3 (`docs/ablation_summaries/phase_3.md`, §4, next-step items 1–3): installing, testing, and uninstalling each of the 30 per-replicate `r2py_kernsmooth` package copies produced by the Phase 1–3 conversion/combine pipeline, and aggregating the resulting `pytest` outcomes by condition, function, and test category. A previously unexercised packaging-metadata defect (PEP 639 non-compliance in `pyproject.toml`'s `license`/`license-files`/classifier fields, present identically in all 30 ablation copies and in the reference `r2py_kernsmooth/`) was discovered, diagnosed, and — with explicit user authorization — repaired via two rounds of targeted `sed` edits across all 30 files, after which all 30 packages installed successfully. The subsequent 30-cycle install/test/uninstall run (≈37 minutes wall-clock, sequential due to a shared pip package name) completed with zero install failures and produced 15,540 individual test outcomes (518 tests × 30 packages). Because the ablation design's 10-replicates-per-condition structure exists specifically to characterize LLM-to-LLM run variance, results were aggregated with the replicate — not the individual test — as the statistical unit: each replicate's total failure count was computed first, and mean/standard-deviation/min/max were then taken across the 10 replicates within each condition, at three levels of granularity (whole-condition, condition × function, and condition × function × test-category). This exposed run-to-run variance large enough, relative to the between-condition differences, to caution against reading small mean gaps (e.g. `guides` vs. `placebo`) as reliable signal without further statistical testing.

### 2. Methodology & Actions Taken

#### 2.1 Initial reconnaissance of the 30-package layout and target environment

- Enumerated `ablation/conversion_guides/{guides,no_guides,placebo}/{1..10}_kernsmooth/` (30 directories total) via `find`, confirming each contains the full Meson/`f2py` package tree inherited from `r2py_kernsmooth/` (Fortran sources under `src/`, `_KernSmoothmodule.c`, `meson.build`, `pyproject.toml`, `pip_install.sh`, and a `tests/` directory) plus a `r2py_kernsmooth/__init__.py` populated by the Phase 3 combine step.
- Confirmed via `conda env list` and `which`/`--version` checks that the `r-to-python` conda environment (activated via `source /software/c/conda/26.3.2/etc/profile.d/conda.sh; conda activate r-to-python`) already provides a working toolchain without any container/Apptainer indirection: system `/usr/bin/gcc` (11.5.0) and `/usr/bin/gfortran`, Python 3.14.4, `pip` 26.1.1, `pytest`, and a `gcc/15.2.0` environment module (`module load gcc`) available but, as later confirmed, not load-bearing for the packaging-metadata failure.

#### 2.2 Discovery and diagnosis of the `pyproject.toml` PEP 639 defect

- First `pip install --no-build-isolation .` attempt (in `ablation/conversion_guides/guides/1_kernsmooth/`) failed during metadata generation with: `meson-python: error: "project.license-files" must not be used when "project.license" is not a SPDX license expression`, traced to `pyproject.toml`'s `license = { text = "Unlimited" }` combined with `license-files = ["LICENSE", "NOTICE"]` — a legacy (pre-PEP 639) table-form `license` field that current `meson-python` (0.19.0) rejects when `license-files` is also present.
- Investigated why the reference `r2py_kernsmooth/` package had never surfaced this defect: `pip show r2py_kernsmooth` returned "not found" in the environment, and `r2py_kernsmooth/build/cp314/meson-logs/meson-log.txt` showed the package had only ever been built via direct `meson setup build && meson compile -C build` (dated 2026-05-21 16:05, with an adjacent `.pytest_cache` dated 2026-05-20) — a path that invokes Meson directly and never triggers `meson-python`'s PEP 517 metadata-generation hook, so the check had simply never been exercised, not previously satisfied.
- Per explicit user redirection ("Why don't you look at `r2py_kernsmooth/pip_install.sh`?"), read that script and reproduced its exact recipe (`module load gcc; conda activate r-to-python; pip install --no-build-isolation .`) against the base `r2py_kernsmooth/` package itself, obtaining the identical `license-files`/SPDX error — confirming the defect is genuine, pre-existing, and independent of the specific invocation path used, rather than an artifact of a deviation from the documented install procedure.
- Presented three remediation options via `AskUserQuestion` (patch the 30 ablation `pyproject.toml` files; downgrade `pip`/`meson-python` instead; or halt for further investigation); user selected the patch option, explicitly scoped to the ablation copies (the reference `r2py_kernsmooth/pyproject.toml` was deliberately left untouched, being out of the request's scope).

#### 2.3 Two-round `pyproject.toml` remediation across all 30 files

- Round 1: `grep -rl 'license = { text = "Unlimited" }' ablation/conversion_guides/{guides,no_guides,placebo}/*_kernsmooth/pyproject.toml` confirmed all 30 files matched; applied `sed -i 's/license = { text = "Unlimited" }/license = "LicenseRef-Unlimited"/'` uniformly across all 30.
- Re-attempted install on `guides/1_kernsmooth`: a second, distinct `meson-python` error surfaced — `Setting "project.license" to an SPDX license expression is not compatible with 'License ::' classifiers` — because PEP 639 forbids trove `License ::` classifiers once `project.license` is an SPDX expression, and each `pyproject.toml`'s `classifiers` list retained `"License :: Freely Distributable"`.
- Round 2: applied `sed -i '/"License :: Freely Distributable",/d'` across all 30 files to drop the now-incompatible classifier line; verified via `grep -c` that zero files still contained it.
- Re-attempted install on `guides/1_kernsmooth` a third time: succeeded cleanly (`Successfully built r2py_kernsmooth`, wheel `r2py_kernsmooth-0.1.0-cp314-cp314-linux_x86_64.whl`, `Successfully installed r2py_kernsmooth-0.1.0`). A full `pytest tests -q` run against this installation (499 passed, 19 failed, 134 warnings, 116.47 s) and a subsequent `pip uninstall -y r2py_kernsmooth` were used as an end-to-end dry run before scripting all 30 packages, confirming the full install → test → uninstall cycle was mechanically sound.

#### 2.4 Confirmation of test-suite uniformity across replicates/conditions

- Compared directory listings of `tests/` across `guides/1`, `guides/2`, `no_guides/1`, and `placebo/1` via `md5sum` on sorted `ls` output — identical (`439afbeafb86e80535cb6d237259f3b9`) — establishing that all 30 packages carry the same 24-file test suite (a set fixed prior to this session, not regenerated per replicate).
- Verified byte-for-byte identity of individual test files across conditions/replicates via `diff` (e.g. `test_bkde2D_edge.py` identical between `guides/1`, `no_guides/1`, `placebo/3`, and `guides/5`), which later justified reconstructing per-test results for a collection failure (§2.6) from a reference replicate rather than re-deriving them independently.
- Catalogued the 24 test files' naming scheme: `test_<function>_{edge,negative,positive}.py` for seven functions (`bkde`, `bkde2D`, `bkfe`, `dpih`, `dpik`, `dpill`, `locpoly` — 21 files); two un-suffixed "general" regression files ported from the original R test suite (`test_bkfe.py`, translated from `KernSmooth/tests/bkfe.R`, and `test_locpoly.py`); and a bare `test.py` smoke script (`import r2py_kernsmooth; bkde(...)`) that — confirmed empirically, since it appeared as zero collected tests in every one of the 30 JUnit reports — is never collected by `pytest`'s default `python_files` glob (`test_*.py`/`*_test.py`), as `test.py` matches neither pattern.
- Counted `^def test_` occurrences (487) versus the JUnit-reported total (518) for a reference package, establishing that the discrepancy (31 additional cases) arises from `@pytest.mark.parametrize`-expanded test IDs, and that raw `grep` counts are therefore unsuitable as a reference for per-module expected-test counts — motivating the JUnit-derived reference-count approach used in §2.6.

#### 2.5 Scripted, sequential install/test/uninstall run

- Authored `run_ablation_tests.sh` (written to the session scratchpad, not committed to the repository) iterating `for COND in guides no_guides placebo; for REP in 1..10`, and for each of the 30 `{COND}/{REP}_kernsmooth` directories: `pip install --no-build-isolation .` (logged to `<name>_install.log`; on failure, recorded `INSTALL_FAILED` in `<name>_status.txt` and skipped to the next package without testing); on success, `pytest tests -q --junitxml=<name>.xml` (logged to `<name>_pytest.log`); `pip uninstall -y r2py_kernsmooth` (logged to `<name>_uninstall.log`); and a cleanup pass removing any `__pycache__`/`.pytest_cache` directories regenerated inside the package tree.
- Executed strictly sequentially — not in parallel across replicates — because all 30 packages share the identical `pyproject.toml` project name (`r2py_kernsmooth`), so concurrent installs would collide in the shared environment's `site-packages`.
- The script exceeded the tool's 120 s foreground timeout and was automatically moved to a background task (ID `b0973r8du`); progress was checked twice via `tail`/status-file counts (11/30 complete at the first check, all 10 `guides` replicates plus one `no_guides` in progress) before a completion notification arrived.
- Total wall-clock time for all 30 cycles, measured from the first install log's timestamp (13:43:08) to the last uninstall log's timestamp (14:20:04): approximately 37 minutes, i.e. roughly 74 seconds/package average for install + test + uninstall combined (individual `pytest` phases alone ranged ≈114–145 s per package based on sampled logs for `guides_1`, `no_guides_5`, `placebo_10`).
- Post-run verification: 30/30 `*_status.txt` files and 30/30 `*.xml` JUnit reports present; `grep -l INSTALL_FAILED` across all status files returned zero matches (no package failed to install); the script's own `ALL DONE` sentinel was present in the captured output.

#### 2.6 JUnit XML parsing and resolution of a whole-module collection-failure anomaly

- Wrote `parse_results.py` to walk all 30 `*.xml` files (schema: `<testsuites><testsuite errors= failures= skipped= tests= time= .../><testcase classname="tests.test_<function>[_<category>]" name="..."/>...`), deriving `function`/`test_category` from each `testcase`'s `classname` via suffix-matching against `{edge, negative, positive}` (anything else classified `general`), and recording a per-test `outcome` of `passed`/`failed`/`skipped`.
- One parsing anomaly required resolution: 23 `testcase` entries in `no_guides_1.xml` carried an empty `classname` with `name` set to a dotted module path instead of a test-function name — the JUnit representation of a whole-module `pytest` *collection* error, one per affected test module (every module except `test.py`, which per §2.4 is never collected at all). Root-caused via the corresponding `no_guides_1_pytest.log`: every affected module fails at `import r2py_kernsmooth` with `ModuleNotFoundError: No module named 'r2py_kernsmooth.bkfe'`, traced to line 10 of the installed `ablation/conversion_guides/no_guides/1_kernsmooth/r2py_kernsmooth/__init__.py`, which contains `from .bkfe import bkfe` — a relative import to a submodule that does not exist in this single-file package layout (the Phase 3 combine step is documented, per `docs/ablation_summaries/phase_3.md` §2.6, to normally strip exactly this class of stale multi-module relative import when co-locating functions into one file; this is the one replicate, of 30, where that step evidently failed to do so). Because all 30 packages carry byte-identical test files (§2.4), the full set of test names normally collected from each of the 23 affected modules was reconstructed from the 29 packages where collection succeeded, and one synthetic `outcome="failed"` row was emitted per reconstructed test name — restoring `no_guides_1`'s row count to the uniform 518-test baseline (23 modules × their respective reference counts = exactly 518 synthetic rows) rather than leaving it undercounted at the module level. This is a substantive, condition-attributable finding (a `no_guides`-specific combine-step failure) and was preserved as data rather than excluded (see §3).
- This produced `raw_test_results.csv` (15,540 rows — 518 tests × 30 packages exactly — columns `condition, replicate, function, test_category, test_name, outcome`), the full per-test-case ledger underlying every subsequent aggregate.
- Aggregation was then built around the replicate as the unit of analysis, in three tiers of granularity, each computed the same way — first summing each replicate's failed/total test counts within the grouping cell, then taking the mean, standard deviation, min, and max of the 10 (condition, replicate) failure counts within each cell — rather than pooling all 5,180 (condition-level) or 15,540 (grand-total) individual test outcomes into a single rate, which would treat tests from the same LLM-generated package as independent observations and understate run-to-run variance:
  1. **`condition`** (3 rows) — every test in the package collapsed to one number per replicate, i.e. the package's overall pass/fail outcome, then averaged across the 10 replicates per condition.
  2. **`condition_function`** (21 rows = 3 conditions × 7 functions) — the four test categories (`edge`/`negative`/`positive`/`general`) collapsed within each function, then averaged across replicates.
  3. **`condition_function_category`** (69 rows = 3 conditions × 23 function/category combinations) — full original granularity, unaggregated across functions or categories, still averaged across the 10 replicates.
- These three tiers (93 rows total) were written to a single file, `failed_tests_summary.csv`, distinguished by a `level` column, with common columns `condition, function, test_category, n_replicates, tests_per_replicate, total_tests_all_replicates, total_failed_all_replicates, failed_mean_per_replicate, failed_std_per_replicate, failed_min, failed_max, pass_rate` (rows with a collapsed dimension carry the sentinel value `ALL` in `function` and/or `test_category`). A companion file, `per_replicate_totals.csv` (30 rows: `condition, replicate, total_tests, total_failed, pass_rate`), was also written to expose the raw per-experiment numbers underlying the `level="condition"` tier directly, without requiring re-derivation from the full 15,540-row ledger.
- All three files were copied into the repository, initially to a newly created `ablation/results/` directory; per explicit user correction ("Of course the folder `results/` should be in `ablation/conversion_guides/`"), relocated to `ablation/conversion_guides/results/` and the now-empty `ablation/results/` removed. Final `git status` confirmed a clean tree modulo the 30 intentionally modified `pyproject.toml` files and the new, as-yet-uncommitted `ablation/conversion_guides/results/` directory (no commit was made, consistent with not having been explicitly requested).

### 3. Key Findings & Results

- **Packaging defect was universal and previously latent, not newly introduced**: all 30 ablation `pyproject.toml` files, and the reference `r2py_kernsmooth/pyproject.toml` itself, carried an identical PEP 639-incompatible `license`/`license-files`/classifier combination. It had never been exercised because the only prior build of `r2py_kernsmooth/` bypassed `pip`/`meson-python` metadata generation entirely (direct `meson setup`/`meson compile`). Fixed, for the 30 ablation copies only, via two `sed`-based edits per file: `license = { text = "Unlimited" }` → `license = "LicenseRef-Unlimited"`, and deletion of the `"License :: Freely Distributable"` classifier line.
- **All 30 packages installed successfully** after remediation (zero `INSTALL_FAILED` entries), each producing a `cp314-cp314-linux_x86_64` wheel and installing/uninstalling cleanly under `r-to-python`'s `pip` without leaving stray build artifacts in the repository tree (confirmed via `git status`).
- **518 tests per package, 15,540 total observations, 30 independent replicate-level experiments.** Condition-level failure counts, aggregated as mean ± std across each condition's 10 replicates (out of 518 tests/replicate):

  | condition | mean failed | std | min | max | pass rate |
  |---|---|---|---|---|---|
  | `guides` | 56.8 | 46.6 | 17 | 126 | 89.0% |
  | `placebo` | 46.3 | 34.2 | 19 | 135 | 91.1% |
  | `no_guides` | 131.2 | 146.0 | 18 | 518 | 74.7% |

  The standard deviation is comparable to or larger than the mean in **every** condition — this is the dominant feature of the dataset. `guides` alone spans a 17-to-126 range (a 7-fold swing between its best and worst replicates) with no evident structure, indicating that LLM run-to-run variance is large relative to whatever effect the condition itself has. Under this variance, the raw mean gap between `guides` (56.8) and `placebo` (46.3) is not distinguishable from noise and should not be read as evidence that withholding the conversion guides *helped* — it is presented as a numeric observation, not a validated effect, pending the significance testing recommended in §4. `no_guides`'s much larger mean and std are driven in part by replicate 1's complete collection-failure outlier (518/518, see §2.6); excluding that single replicate, `no_guides`'s remaining 9 replicates give mean 88.2, std 72.3, min 18, max 230 (pass rate 83.0%) — still the clear high-failure outlier among the three conditions, but as "elevated and noisy" rather than "uniformly catastrophic."
- **Function-level aggregation** (`condition_function` tier, four categories collapsed per function) surfaces the functions driving both the overall means and their variance:
  - `dpik` and `dpih` show the cleanest condition ordering (guides best, no_guides worst) and comparatively low variance — the closest this dataset comes to a clean ablation signal.
  - `dpill` and `locpoly` are simultaneously the two hardest functions (highest absolute failure rates in all three conditions) and the two most volatile, with `placebo` numerically outperforming `guides` on both — the primary source of the `guides`-vs-`placebo` inversion visible at the condition level.
  - `bkde`, `bkde2D`, and `bkfe` show comparatively small, low-variance differences between conditions.
- **Full-granularity (`condition_function_category`) tier** — selected cells, `failed_mean_per_replicate` out of `tests_per_replicate`, mean across 10 replicates:
  - `dpik_positive` (52/replicate): guides 2.6 (5.0%), placebo 7.2 (13.8%), no_guides 12.8 (24.6%) — expected ordering, low relative variance.
  - `dpih_positive` (32/replicate): guides 1.3 (4.1%), placebo 2.7 (8.4%), no_guides 8.0 (25.0%) — same ordering.
  - `dpill_positive` (38/replicate) — the single worst-performing cell overall: no_guides 20.7 (54.5%), guides 17.8 (46.8%), placebo 14.3 (37.6%).
  - `locpoly_positive` (38/replicate): no_guides 13.5 (35.5%), guides 11.4 (30.0%), placebo 3.8 (10.0%).
  - `dpill_edge` (28/replicate) is uniformly weak across all three conditions (no_guides 13.6/48.6%, placebo 9.2/32.9%, guides 11.6/41.4%), suggesting a difficulty intrinsic to the category rather than one differentiating conditions.
  - Zero-failure cells occur in all three conditions for `bkde_negative`, `bkde2D_negative`, `dpih_edge`, `dpik_edge`, and `dpill_negative` — apparently easy regardless of guide availability.
- **One package-level anomaly, retained as data**: `no_guides` replicate 1's assembled `__init__.py` retains an unresolved `from .bkfe import bkfe` relative import, causing complete `ImportError`-driven collection failure across 23 of 24 test modules — its entire 518-test suite fails, making it the single worst-performing replicate in the dataset by a wide margin and the principal driver of `no_guides`'s inflated variance (§2.6, above). It is preserved as a genuine `no_guides`-condition combine-step failure mode rather than excluded or treated as a measurement artifact.

### 4. Conclusion & Next Steps

The session's objective — installing, testing, and uninstalling all 30 ablation-condition `r2py_kernsmooth` replicates and summarizing `pytest` outcomes by condition, function, and test category, with the replicate treated as the unit of statistical aggregation appropriate to a 10-replicates-per-condition design — is complete. A previously unexercised, repository-wide packaging-metadata defect was identified and remediated (scoped strictly to the 30 ablation copies, at explicit user direction) as a precondition for any of the 30 installs to succeed; the subsequent full test run completed without infrastructure failures, and one substantive package-level defect (`no_guides` replicate 1's broken relative import) was investigated to its root cause and retained as data rather than treated as noise. Three CSV artifacts now sit in the working tree at `ablation/conversion_guides/results/`: `raw_test_results.csv` (full per-test granularity, 15,540 rows), `per_replicate_totals.csv` (the 30 per-experiment totals), and `failed_tests_summary.csv` (a three-tier — condition / condition×function / condition×function×category — mean/std/min/max rollup across the 10 replicates per condition, 93 rows). These provide the correctness/behavioral metrics flagged as the outstanding deliverable at the end of Phase 3, computed in a form that surfaces rather than obscures inter-replicate variance. Neither the CSVs nor the 30 modified `pyproject.toml` files have been committed to git as of session end (no commit was requested). Immediate next steps, none undertaken in this session: (1) formal statistical testing (e.g. a paired or bootstrap comparison per function, given the small n=10 per condition and the demonstrated within-condition variance) before treating any condition-level or function-level gap — particularly the `guides`-vs-`placebo` inversions on `dpill`/`locpoly` — as a reliable effect rather than sampling noise; (2) qualitative inspection of `no_guides` replicate 1's `__init__.py` and its originating `all.R/*.json` combine inputs to determine whether the stray `from .bkfe import bkfe` import reflects a systematic no-guides-condition failure mode or an isolated one-off, and whether it should be treated as an outlier to exclude or as a legitimate condition effect to retain in any formal analysis; (3) a decision on whether to commit the `pyproject.toml` remediation and the new `results/` directory, and whether the same PEP 639 fix should be back-ported to the reference `r2py_kernsmooth/pyproject.toml` to make it independently `pip`-installable; (4) extension of this build-and-test protocol, including its replicate-level aggregation methodology, to the confirmatory-tier `rpart` run referenced as a future stage in Phase 3's own next-steps list.
