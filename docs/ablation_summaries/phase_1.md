# Research Report: r2py Ablation Protocol — Phase 1 (Protocol Review, Placebo-Condition Materials, and HPC Execution Infrastructure)

**Repository**: `python-KernSmooth` (branch `main`)
**Session scope**: Review of the pre-registered ablation protocol; generation and validation of Condition-P (placebo) conversion-guide materials; design, debugging, and provisioning of unattended HPC execution infrastructure (SGE array job + Apptainer container) for Condition-G batch runs of the `@convert-r-function-to-python` pipeline.

---

### 1. Abstract

This session covered three linked work-streams: (1) ingestion and structured summarization of the project's pre-registered ablation protocol (`docs/ablation_protocol_20260719.pdf`), which tests whether pre-generated R→Python conversion guides reduce silent translation error relative to no-guide and placebo-instruction controls; (2) construction of the Condition-P (placebo) experimental materials — a single generic, construct-agnostic instruction document replicated across all 46 language-dependency constructs into `ablation/conversion_guides/placebo_conversion_guides/`; and (3) the design, empirical validation, and provisioning of a fully unattended execution path for Condition-G batch conversions on the project's SGE-scheduled HPC cluster, culminating in a working, locally built Apptainer container image (`ablation/claude_env.img`, 234 MB) that runs the Claude Code CLI headlessly with the `r-to-python` conda environment active by default. The session ends with all three deliverables in place and functionally verified (though the 10-replicate Condition-G production run itself was not launched), plus an explicit recommendation against committing the built container image to version control.

### 2. Methodology & Actions Taken

#### 2.1 Protocol review
- Read `docs/ablation_protocol_20260719.pdf` (8 pages, dated 2026-07-19) in full via the PDF-capable `Read` tool.
- Noted the existence of a same-week revision, `docs/ablation_protocol_20260719_v2.pdf` (modified 2026-07-22, 210,350 bytes vs. the original's 180,008 bytes), flagged to the user but not itself read in this session.
- Extracted and reported the protocol's full structure: **Purpose/Scope** (motivated by the `linbin`/`rlbin` divergence anecdote from KernSmooth Phase 4, where one independent conversion-agent invocation subscripted a `None` f2py return while a structurally near-identical sibling function used correct in-place semantics); **Hypotheses** H1 (correctness — pass-rate on R-benchmarked oracle), H2 (consistency — idiom dispersion), H3 (error character, exploratory — silent vs. loud failure skew); **Experimental Design** with three conditions — **G** (guides, full treatment), **N** (no guides, guide-injection block removed with no other change), **P** (placebo, generic construct-agnostic instruction block of comparable token length, explicitly designed to rule out "more context helps" as a confound); the **substitution harness** (splice one converted function into an already-validated package — `r2py_kernsmooth` at 518/518 tests, `r2py_rpart` at 844/846 — run the mutation-derived exercising test subset, then restore); the **function sample** (Primary tier: all KernSmooth functions with non-empty exercising subsets, ~16 functions/7 public; Confirmatory tier: stratified rpart sample of 12–15 functions over-representing high-risk constructs `as.integer`, `unlist`, `tapply`, `t`, `format`, `switch`, `missing`); **replication/power** (pilot = 5 functions × {G,N} × 3 replicates = 30 invocations; planned R=10 replicates/cell, ≈480 invocations primary tier, ≈450 confirmatory tier, cross-referenced against the project's prior scale of 172-agent/9-batch dispatch in rpart Phase 8.2); **outcome measures** (H1: binary pytest pass/fail; H2: idiom-dispersion metric $D_k = |\{\text{normalise(translation of } k \text{ at site } s)\}|$ over constructs with ≥3 call sites; H3: three-way failure taxonomy — silent numerical / loud / structural); **contamination** as the principal validity threat (argued to bias toward the null, quantified via a per-function memorization probe, addressable via a held-out third-package arm on `acepack` or `logspline`); **randomization/blinding/pre-registration** requirements; the **fixed analysis plan** (H1: mixed-effects logistic regression with function as random intercept, plus a distribution-free paired Wilcoxon robustness check; H2: paired Wilcoxon signed-rank by construct; H3: Fisher's exact test or descriptive-only if underpowered); **threats to validity** (contamination, oracle incompleteness, single-function isolation, single-model-family generality, construct-frequency imbalance); and the **9-step execution sequence** (harness/test-map → freeze prompts/normaliser → memorization probe → pilot → pre-register → primary tier → confirmatory tier → optional held-out arm → unblind/analyze).

#### 2.3 Condition-P (placebo) material construction
- Per protocol §3.1, drafted a single generic, **construct-agnostic** placebo document titled "## Conversion Guide: General R-to-Python Translation Notes," containing eight sections: (1) General Instruction, (2) Indexing and Ranges (1-based vs. 0-based, inclusive `a:b` ranges), (3) Types and Coercion (R's implicit coercion vs. NumPy's strictness), (4) Vectorization and Shape (dimension-dropping edge cases), (5) Missing Values and Edge Cases (`NA` vs. `NaN`/`None`), (6) Numerical Conventions (denominator conventions, rounding modes, transcendental-function argument order), (7) Style and Naming (idiomatic NumPy/SciPy preference, auditability), (8) Verification (manual trace-through discipline). Deliberately excludes any function-specific analysis, R source citation, or file/line reference, in contrast to the real guides' schema (§2.2), so as to isolate "generic instruction of comparable length" as the manipulated variable per the protocol's Condition-P design rationale.
- Measured the draft: **4,265 characters, 51 lines** — within the real corpus's observed 3,295–7,376-character range and close to its 4,610.93-character mean (92.5% of mean); line count is naturally lower than the 122.09-line mean because the placebo is prose-only with no code blocks or tables, which inflate the real guides' line counts.
- Created target directory `ablation/conversion_guides/placebo_conversion_guides/` and copied the single placebo file to all 46 filenames matching the real corpus's naming exactly.
- Verified correctness two ways: (a) `diff` between the sorted filename listing of the new directory and the real corpus's filename listing — confirmed identical (`FILENAMES MATCH`); (b) `md5sum` across all 46 copies reduced to **exactly one unique hash**, confirming byte-for-byte identical content across every file as intended (a single placebo instruction block reused for every construct, not 46 independent placebo texts).

#### 2.6 SGE array-job script development
- Authored `ablation/submit_guides_replicates.sh` (initial location before a later move) as an **SGE array job**: `#$ -N ablation_guides`, `#$ -t 1-10` (array with 10 tasks, `$SGE_TASK_ID` supplying the replicate index automatically — eliminating any need for manual `#`-substitution or an external loop), `#$ -cwd`, `#$ -j y` (merge stderr into stdout), `#$ -o ablation/logs/guides_$TASK_ID.log`, and an initial `#$ -q hpc` queue directive. - Explicitly documented in-script the risk trade-off of `--dangerously-skip-permissions`: with no terminal attached in a headless/array job, every downstream tool call the conversion agent issues (file writes, bash commands, etc.) executes without any human checkpoint for the full job duration — a deliberate, necessary consequence of the "no privilege-granting human present" requirement, not an oversight.
- User asked the function of the directive `#$ -N ablation_guides` specifically; explained it is an SGE/Grid-Engine job-control directive (parsed by `qsub`, not shell syntax) that sets the job's display name in `qstat`, seeds default log-file naming when `-o`/`-e` are not overridden, and is the handle used for `qdel`.
- User moved the script (independently) to `ablation/conversion_guides/submit_guides_replicates.sh`; the internal `qsub ...` path comment was updated to match.

Re-validation performed: `bash -n` syntax check (passed); confirmed `long` is a valid live SGE queue via `qconf -sql` (`gpu`, `hpc`, `largemem`, `long`); found and fixed two real defects — (a) the script was not executable (`-rw-r--r--`), corrected via `chmod +x`; (b) `ablation/logs/` (required to pre-exist for SGE's `-o` spooling) did not exist, created via `mkdir -p`. #### 2.9 Advisory on version control of the built image
- User asked whether `claude_env.img` should be pushed to GitHub. Recommended **against** it, on three grounds: (1) at 234 MB the file exceeds GitHub's 100 MB hard per-file push limit and would require Git LFS to store at all; (2) the artifact is already gitignored and fully and rapidly reproducible from the two version-controlled sources (`ablation/claude_env.def` + `ablation/build_claude_env.sh`), making the binary redundant to commit; (3) the image bundles third-party redistributable software (the Node.js runtime and npm-registry packages, including `@anthropic-ai/claude-code`) into an opaque blob, which raises licensing/provenance concerns inappropriate for a research-paper repository — the `.def` file is the auditable source of truth and should remain the artifact under version control.

### 3. Key Findings & Results

- **Corpus statistics (Condition-G real guides)**: 46 files, 5,616 total lines, 212,103 total characters; mean 122.09 lines/file, mean 4,610.93 characters/file; range 3,295–7,376 characters/file.
- **Placebo material (Condition P)**: single 8-section, construct-agnostic document, 4,265 characters / 51 lines, replicated byte-identically (single MD5 hash across all 46 copies) into `ablation/conversion_guides/placebo_conversion_guides/`, with filenames verified identical to the real corpus via `diff`.
- **Scheduler landscape**: this cluster runs SGE (queues `gpu`, `hpc`, `largemem`, `long` — `hpc` observed at CQLOAD 0.84, 6,926/9,632 slots used at time of inspection) alongside HTCondor; user selected SGE for this workload.
- **No admin-level `claude` install exists or is obtainable** on this system; this was the hard constraint driving the entire containerization work-stream.
- **No Apptainer/Singularity environment module exists**, but both tools are present system-wide (v1.5.0-1.el9) with no module load required — a discrepancy between the module system and actual tool availability worth remembering for future HPC work in this environment.
- **Unprivileged (`--fakeroot`) container builds work on this cluster despite no admin-configured `/etc/subuid`/`/etc/subgid` entry for the user**, via Apptainer's automatic "root-mapped namespace" fallback — empirically confirmed across three independent test builds (plain image conversion, privileged `apt-get install`, and `npm install -g`), not merely asserted from documentation.
- **`claude` CLI installs cleanly via npm inside a `node:22-slim`-based container**: package `@anthropic-ai/claude-code`, resulting version `2.1.217 (Claude Code)`, confirmed reproducibly across the scratch test build and the final production build.
- **Cluster mount defaults**: `$HOME` is auto-bound into every Apptainer container on this system (`mount home = yes`); `/software` and `/groups` are **not** (`mount hostfs = no`, no corresponding `bind path` entries) — confirmed both by reading `apptainer.conf` and by direct empirical test (`ls` inside a container succeeding for a `~`-relative path, failing for `/groups/...`).
- **Conda-environment activation strategy validated**: because `~/.conda/envs/r-to-python` sits under the auto-bound `$HOME` while the conda **base** install does not, prepending the environment's own `bin/` directory to `PATH` at container runtime (via the `.def` file's `%environment` block) correctly activates `Python 3.14.4` from that environment without requiring `/software` to be bound or the real `conda activate` machinery to be present — verified by direct execution inside a test container.
- **Final deliverables, all present and independently verified working**:
  - `ablation/conversion_guides/placebo_conversion_guides/` — 46 identical placebo guides.
  - `ablation/claude_env.def` — Apptainer definition (Node 22-slim base, `@anthropic-ai/claude-code` via npm, `r-to-python` env auto-activated via `PATH`).
  - `ablation/build_claude_env.sh` — executable build wrapper (subsequently annotated with SGE `#$ -pe smp 1` / `#$ -q long` directives by the user/linter).
  - `ablation/claude_env.img` — built SIF image, 245,432,320 bytes, confirmed functional (`claude --version` → `2.1.217`) both immediately post-build and via a fresh `apptainer exec --bind /groups ...` invocation.
  - `ablation/conversion_guides/submit_guides_replicates.sh` — SGE array-job script (`-t 1-10`, queue `long`, executable, logs directory pre-created), updated to route the `claude` invocation through the container with the required `--bind /groups`.
  - `.gitignore` updated with `ablation/claude_env.img`.
